La frase de apertura

MT5 registra lo que ocurrió; nosotros registramos por qué tomamos la decisión. Supabase conserva ambas cosas, Telegram facilita escribirlas y Vercel las muestra.

Recorrido en pantalla

Minutos Mostrar / hacer Qué explicar
0–2 Dashboard con datos de la demo La web vive en Vercel; los datos, permisos y receptores viven en Supabase
2–4 Mapa de la configuración y funciones Proyecto propio → SQL → receptor → clave de cuenta → EA → bot → web
4–6 Recepción reciente y HTTP 200, sin mostrar inputs secretos El EA v3.40 se compiló, está activo y se verificó recepción; un binario por sí solo no prueba conexión
6–9 Una operación con apertura y cierre Separar comentario nativo, motivo humano y resultado; aclarar qué textos son de muestra
9–12 En el bot: /dashboard; en la web: Entrar con Telegram Copiar el código privadamente, editar un motivo elegido y mostrar su historial; no mostrar el código al público
12–14 Dashboard desde el celular o ventana estrecha Misma información en tarjetas; lectura pública, edición solo del propietario
14–15 Resumen de instalación y prompt Cada alumno crea sus recursos y verifica cada tramo con su agente

Si no quieres modificar ningún motivo durante la presentación, muestra el editor y su historial y cancela sin guardar. No es necesario abrir o cerrar un trade.

Antes de compartir pantalla

  • Abrir la URL de producción, el chat privado del bot y esta ayuda memoria.
  • Comprobar recepción reciente con Actualizar y MT5 conectado.
  • Tener elegida una operación existente; si es una muestra, decirlo al presentarla.
  • Mantener fuera de la pantalla los inputs del EA, Secrets, connection.json, .set privados y códigos de acceso. No abrir esos archivos para explicar las claves.
  • Probar el acceso al editor antes de la clase; no confundir pruebas del agente con una sesión de edición comprobada por el propietario.
  • No compartir una URL Git heredada como si ya contuviera este trabajo: consultar ENTREGA.md. La publicación Git del seminario 3 está pendiente.

Recordatorio Valor / explicación
Secret del bot TELEGRAM_BOT_TOKEN, exactamente así

Qué está demostrado y qué no prometer

En el entorno docente se verificaron compilación v3.40 con 0 errores y 0 advertencias, recepción real, dashboard público, vinculación del bot y motivos guardados. Se verificó la interfaz móvil y existen pruebas controladas de edición y protecciones. La primera sesión real de edición del propietario y el recorrido completo de un cambio SL/TP con su motivo siguen sujetos a la evidencia del registro actual; no presentarlos como certificados por los tests.

La muestra revisada tiene 102 operaciones: se añadieron 199 motivos de muestra y se conservaron cinco del propietario. Después se abreviaron los textos visibles a petición del docente. Su origen sintético queda en historial y documentación: no son evidencia de señales reales ni del razonamiento del trader. Los alumnos pueden usarlos para entender el formato, no para validar estrategias.

No prometer entrega instantánea, métricas MAE/MFE, equity histórica ni soporte multiusuario completo. Los filtros y totales del historial se calculan en el servidor; los gráficos y Exportar página corresponden solo a la página actual.

Revisión antes de compartir

  1. Ejecuta el plan de pruebas y revisa el diff.
  2. Comprueba que los archivos nuevos deseados aparezcan en git status --short. Un archivo local sin commit no aparecerá en un clon remoto.
  3. Revisa la exclusión de .local/, .env.local, configuraciones MCP con tokens, archivos *.private.json, binarios compilados y accesos directos *.lnk. No borres los archivos privados del equipo: simplemente quedan fuera de la entrega.
  4. Ejecuta el escáner de publicación. Para el escáner general del proyecto:

sh uv run --locked python tools/install_gitleaks.py .local/tools/gitleaks git --redact --no-banner --log-opts=--all .

El instalador verifica el SHA-256 del binario fijado en el manifiesto. En Windows, usar una instalación oficial compatible y consultar su ayuda. El modo git inspecciona historia: antes de publicar, revisa también el árbol final de archivos seleccionados con el modo dir de Gitleaks. No escanees/exportes toda la carpeta de trabajo como si fuera el contenido público: contiene configuración local ignorada. 5. Comprueba que el build de documentación no contenga configuraciones privadas. 6. Guarda la evidencia de revisión sin secretos; registra qué fue probado y qué queda pendiente.

El escaneo es heurístico y no certifica ausencia absoluta de secretos. Si encuentra algo, revisar la coincidencia sin imprimir el valor y resolver el origen antes de compartir.

Qué significa «probado»

  • Offline: ejecuta código con casos controlados; no contacta servicios.
  • Compilado: el compilador produjo un binario de esa fuente específica.
  • Desplegado: el proveedor aceptó y publicó los archivos; falta comprobar el uso.
  • Recepción real: registros leídos en Supabase y contrastados con el origen.
  • Validado por el propietario: la persona usó su bot o dashboard y confirmó el resultado.

No sustituir una evidencia por otra. No se ha ejecutado el recorrido completo desde un clon limpio por un alumno independiente en Windows, Codex, Claude Code y Antigravity. Los agentes deben adaptar la instalación, no declarar portabilidad probada.
