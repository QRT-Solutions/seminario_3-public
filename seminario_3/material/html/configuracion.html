Este es el paso a paso abreviado para reproducir la instalación con tu agente. Cada alumno usa su propia cuenta demo, proyecto Supabase, bot y proyecto Vercel. Para presentar el recorrido sin reinstalarlo, usa la ayuda memoria de la presentación.

1. Preparar el repositorio y los accesos

  1. Clona la URL entregada por el docente y abre la raíz del repositorio.
  2. Entrega al agente el prompt de instalación. Debe revisar qué existe y aplicar solo lo que falta, conservando tus configuraciones.
  3. Comprueba acceso a Supabase y Vercel, Telegram disponible y MT5 con cuenta demo.
  4. Descubre ambos MCP nativos: terminal en 127.0.0.1:22346 y MetaEditor en 127.0.0.1:22345. El agente lee cuenta, broker y servidor; no los adivina.

Comprobación: cuenta demo identificada y ambos conectores responden. Detalle: preparación del alumno y MT5.

2. Crear Supabase y preparar la base

  1. En Supabase, crea o selecciona un proyecto de tu organización. Revisa región, plan y condiciones antes de crearlo. Guarda la contraseña de base en tu gestor.
  2. Espera a que el proyecto esté disponible y registra su Project URL y Project Ref. Verifica que todas las pantallas y herramientas apunten allí.
  3. Conecta el agente mediante el conector Supabase disponible en tu cliente. Comprueba el proyecto con una consulta de lectura antes de hacer cambios.
  4. En una instalación nueva, aplica las diez referencias SQL en el orden documentado. Si ya existen tablas, compara las migraciones y aplica diferencias; no repitas los archivos completos.
  5. Comprueba las 17 tablas mt5_ esperadas para el recorrido completo, RLS y permisos. Crear la estructura de publicación todavía no hace pública la cuenta.

Comprobación: tablas preparadas, acceso directo público a tablas bloqueado y proyecto correcto. Detalle: configuración Supabase.

3. Desplegar el receptor y generar la credencial del EA

Las funciones son los pequeños programas que reciben y validan cada petición:

Función Trabajo Archivos del paquete definitivo
mt5-telemetry Recibe datos de MT5 y entrega avisos pendientes index.ts, core.mjs, notifications.mjs, deno.jsonc
mt5-telegram Recibe mensajes del bot index.ts, runtime.ts, core.mjs, deno.jsonc
mt5-dashboard-editor Valida códigos y guarda motivos desde la web index.ts, core.mjs, deno.jsonc

Están en seminario_3/supabase/functions/. El agente prueba y despliega primero mt5-telemetry; Telegram y el editor se completan en los pasos siguientes. Los tres ejemplos usan verify_jwt=false porque su código valida su propia credencial. Es una configuración de estos receptores, no una regla para otras funciones.

La credencial mt5_… se genera con el script del repositorio, no desde API Keys de Supabase ni desde el broker. Desde la raíz, sustituyendo los marcadores:

# Autor: QRT Solutions. Sustituir por los datos verificados del alumno.
uv run --locked python seminario_3/supabase/scripts/crear_credencial.py \
  --project-ref TU_PROJECT_REF \
  --login TU_LOGIN \
  --broker "TU_BROKER" \
  --server "TU_SERVIDOR" \
  --project-name "Seminario-3"
  1. El script crea una clave aleatoria y archivos privados en .local/supabase-setup/device/; no imprime el secreto.
  2. El agente revisa y ejecuta register.sql de esa carpeta en tu proyecto. Registra la huella SHA-256 y la identidad autorizada, no el token en texto claro.
  3. Abre connection.json localmente y copia únicamente el valor de token. También está como InpSupabaseKey en parameters.json y en el archivo .set.
  4. La vigencia predeterminada es 90 días. Para renovar, genera en un directorio nuevo con --output, registra, verifica el envío y después revoca la anterior.

Comprobación: generar la clave y registrar su hash son dos pasos distintos; sin registro no funciona. Detalle: receptor y credencial.

5. Crear y conectar Telegram

  1. Abre BotFather oficial, envía /newbot, elige un nombre visible y un usuario disponible terminado en bot.
  2. Guarda el token en el mismo proyecto Supabase → Edge Functions → Secrets, con el nombre exacto TELEGRAM_BOT_TOKEN. Pulsa Save y comprueba la fila. TLG_BOT_TOKEN no es el nombre leído por este código.
  3. El agente prepara el instalador privado:

  --bot-username TU_USUARIO_BOT \
  --output .local/telegram-setup/instalacion-1
  1. El agente despliega temporalmente mt5-telegram con entrada setup.ts y el paquete indicado en la guía de instalación. Luego ejecuta:
# Autor: QRT Solutions. Después del despliegue temporal, antes de su vencimiento.
uv run --locked python seminario_3/integraciones/telegram/configurar_webhook.py \
  --project-ref TU_PROJECT_REF \
  --installation .local/telegram-setup/instalacion-1
  1. El instalador verifica el bot y configura el webhook —la dirección a la que Telegram entrega los mensajes— con message y callback_query. Desplegar inmediatamente el paquete definitivo con index.ts, retirando setup.ts y setup.private.json, también si falló la instalación temporal.
  2. Abre el chat privado de tu bot y pulsa Iniciar. El agente obtiene el account_id de tu snapshot y genera la vinculación:

Comprobación: «Chat vinculado», /pendientes responde y solo el propietario autorizado puede editar. /start abre la conversación; no autoriza la cuenta. La creación del bot y el manejo de Secrets siguen las guías de Telegram y Supabase.

7. Habilitar la edición web mediante Telegram

  1. El agente registra la URL HTTPS de producción, sin barra final, y el usuario del bot, sin @, en mt5_dashboard_web_config.
  2. Despliega mt5-dashboard-editor y comprueba que mt5-telegram incluya /dashboard.
  3. En la web pulsa Entrar con Telegram. Envía /dashboard a tu bot privado.
  4. Copia el código en la web y pulsa Entrar. Vence en cinco minutos y sirve una vez.
  5. Abre una operación → Editar motivo / Completar motivo → Guardar motivo. Consulta Historial y termina con Salir de edición.

La sesión dura una hora; recargar la página la descarta. Los motivos son públicos, pero editarlos exige autorización. Los comentarios originales del broker y los datos financieros permanecen separados. Detalle: editor web.

Para una demostración, basta usar una operación histórica existente. Si el propietario decide operar en demo, el aviso de apertura/cierre permite Responder con la razón; el agente no abre una operación para probar. Los deals históricos no generan una tormenta de avisos: se consultan con /pendientes.

La web consulta el estado cada 30 segundos y el historial cada dos minutos. Los cambios observados de SL/TP se agrupan por posición durante un minuto y su aviso espera la finalización del grupo y una recepción posterior de telemetría. El bot registra su explicación; no cambia los niveles en MT5. No se garantiza entrega instantánea cuando fallan la red o MT5.

6. Uso y prueba real

Avisos automáticos de apertura y cierre

El flujo recomendado ya no requiere copiar referencias: cuando llega un nuevo deal de apertura por evento, el bot envía «Nueva apertura», símbolo, dirección, volumen y precio, y solicita la razón. El usuario pulsa Responder sobre ese mensaje y escribe su motivo verdadero. Telegram suele abrir automáticamente el campo de respuesta gracias a ForceReply.

Cuando llega una salida, el bot envía «Cierre registrado» y pide la razón para cerrar o reducir volumen. Responder directamente a ese aviso guarda el motivo de cierre; responder al de apertura guarda el motivo de entrada. La confirmación indica la fase correspondiente y nunca sobrescribe el motivo de la otra fase.

El servidor resuelve el mensaje original por su identificador almacenado y por el chat autorizado, no por texto citado que pueda falsificarse. Confirma el guardado y permite consultarlo con /ver REFERENCIA. Las correcciones también pueden enviarse como otra respuesta al mismo aviso. No se interpretan mensajes sueltos como motivos de la última operación: así no se asignan a un trade equivocado.

Para activar este flujo en el proyecto del alumno:

  1. Aplicar telegram_alertas_apertura.sql después de las migraciones de bitácora y vinculación y luego telegram_alertas_cierre.sql. No generan alertas antiguas. En una instalación activa, desplegar primero las funciones que distinguen la fase y después aplicar la extensión de cierre.
  2. Desplegar también mt5-telemetry con index.ts, core.mjs, notifications.mjs y deno.jsonc; desplegar mt5-telegram con sus cuatro archivos definitivos.
  3. Verificar en el EA activo InpEventDrivenSync=true, InpExportDeals=true y InpEnableKillSwitch=false. El EA v3.20 dispone del envío por evento requerido.
  4. Vincular primero el chat y esperar la confirmación del agente de que está activo.
  5. Si el propietario decide abrir una operación demo, comprobar recepción del deal, envío del mensaje y guardado de su respuesta. El agente no abre trades de prueba.

La alerta se prepara por cada posición, usuario y fase al insertar un deal BUY/SELL con approval_status=PENDING, la marca usada por el exportador en OnTradeTransaction. IN pide apertura; OUT y OUT_BY piden cierre; INOUT permite ambas fases. No significa aprobación humana. Los lotes históricos APPROVED y deals ya existentes no generan avisos. Una posición tiene como máximo una solicitud por fase y usuario: los aumentos de volumen y cierres parciales posteriores no generan otra solicitud. El primer cierre parcial ya puede pedir motivo; el mensaje no afirma que toda la posición haya quedado cerrada. Esta versión conserva un motivo de salida por posición.

La extensión mantiene los nombres RPC originales que contienen opening para permitir el despliegue sin interrumpir la telemetría; ahora la cola devuelve phase y selecciona el motivo pendiente de esa fase. No basta con cambiar solo el texto del mensaje: también deben ampliarse el CHECK, el trigger y la consulta de la cola. Un aviso omitido antes de activar esta extensión puede recuperarse administrativamente para una operación identificada y verificada, sin reencolar todo el historial.

La cola mt5_telegram_notifications se inserta dentro de la transacción del deal. El receptor inicia la entrega en segundo plano con EdgeRuntime.waitUntil, sin hacer esperar al EA por Telegram. Una reserva temporal evita envíos simultáneos; el identificador de mensaje devuelto por Telegram queda asociado a la posición. Si falla, las siguientes recepciones de telemetría reintentan la cola, con espera mínima de 30 segundos. Si MT5 deja de enviar, esos reintentos también esperan. No hay un cron independiente ni una garantía de latencia o entrega exactamente una vez: un timeout después de enviar y antes de guardar el recibo puede duplicar el aviso. La respuesta escrita se deduplica mediante update_id.

En condiciones normales se espera el aviso en segundos; la medición de una prueba real debe documentarse. Si MT5 pierde el evento de apertura o cierre antes de enviarlo, esta cola no puede recuperar ese evento. No activar trading ni DLL para intentar resolverlo.

Qué significa «probado»

  • Offline: ejecuta código con casos controlados; no contacta servicios.
  • Compilado: el compilador produjo un binario de esa fuente específica.
  • Desplegado: el proveedor aceptó y publicó los archivos; falta comprobar el uso.
  • Recepción real: registros leídos en Supabase y contrastados con el origen.
  • Validado por el propietario: la persona usó su bot o dashboard y confirmó el resultado.

No sustituir una evidencia por otra. No se ha ejecutado el recorrido completo desde un clon limpio por un alumno independiente en Windows, Codex, Claude Code y Antigravity. Los agentes deben adaptar la instalación, no declarar portabilidad probada.

Revisión antes de compartir

  1. Ejecuta el plan de pruebas y revisa el diff.
  2. Comprueba que los archivos nuevos deseados aparezcan en git status --short. Un archivo local sin commit no aparecerá en un clon remoto.
  3. Revisa la exclusión de .local/, .env.local, configuraciones MCP con tokens, archivos *.private.json, binarios compilados y accesos directos *.lnk. No borres los archivos privados del equipo: simplemente quedan fuera de la entrega.
  4. Ejecuta el escáner de publicación. Para el escáner general del proyecto:

sh uv run --locked python tools/install_gitleaks.py .local/tools/gitleaks git --redact --no-banner --log-opts=--all .

El instalador verifica el SHA-256 del binario fijado en el manifiesto. En Windows, usar una instalación oficial compatible y consultar su ayuda. El modo git inspecciona historia: antes de publicar, revisa también el árbol final de archivos seleccionados con el modo dir de Gitleaks. No escanees/exportes toda la carpeta de trabajo como si fuera el contenido público: contiene configuración local ignorada. 5. Comprueba que el build de documentación no contenga configuraciones privadas. 6. Guarda la evidencia de revisión sin secretos; registra qué fue probado y qué queda pendiente.

El escaneo es heurístico y no certifica ausencia absoluta de secretos. Si encuentra algo, revisar la coincidencia sin imprimir el valor y resolver el origen antes de compartir.
